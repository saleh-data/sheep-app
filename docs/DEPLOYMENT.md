# دليل الإعداد

## مشروع Sheep الحالي

طُبّقت ملفات `supabase/migrations` ونُشرت دالة رفع الصور بالفعل في المشروع `euubvvspzolxuclnords`. لا تُعِد تنفيذ CREATE TABLE عليه. لم تُنشأ حسابات أو سجلات تجريبية.

## مشروع جديد بديل

1. أنشئ منظمة وخطة **Free** في Supabase ثم مشروعًا واحدًا؛ لا تختَر مزايا مدفوعة. احفظ كلمة مرور قاعدة البيانات في مدير كلمات المرور.
2. من SQL Editor شغّل ملفات `supabase/migrations/*.sql` بالترتيب التصاعدي. تشمل الجداول، القيود، الفهارس، RLS، الدوال، المخزن الخاص وسياسة قراءة المرفقات.
3. من Edge Functions أنشئ `upload-attachment` من ملف `supabase/functions/upload-attachment/index.ts`. عطّل فحص JWT القديم على بوابة الخدمة فقط؛ الكود يتحقق من JWT وحساب الشريك عبر Supabase Auth قبل أي رفع. يتوافق ذلك مع مفاتيح publishable وتوقيعات JWT الحديثة. لا تحذف تحقق `getUser` أو اعتماد الشريك.
4. تأكد من وجود متغيرات Supabase التلقائية داخل الخدمة. الكود يقرأ المفتاح العام والسرّي من متغيرات الخدمة الحديثة، مع fallback إلى متغيرات Supabase القديمة. لا تحتاج نسخ أي مفتاح إداري إلى المشروع المحلي.
5. عدّل عنوان المشروع ومفتاح publishable في متغيرات الواجهة العامة كما في README، ثم أعد البناء.

## إعداد الحسابين — دخول بكلمة المرور فقط

1. افتح مشروع Sheep → Authentication → Users → Add user → Create new user.
2. أدخل `partner1@example.test` وكلمة مرور خاصة به، وفعّل **Auto Confirm User**، ثم أنشئ الحساب. هذا اعتماد إداري ولا يرسل رسالة تأكيد.
3. كرر مع `partner2@example.test` وكلمة مرور مستقلة. لا تختَر Send invitation.
4. قائمة private.signup_allowlist تمنع إنشاء أي بريد آخر؛ تُضاف الحسابات المؤكدة تلقائيًا إلى partners. لا تكتب كلمات المرور في جداول البيانات أو SQL أو المحادثة.
5. من إعدادات Auth عطّل **Allow new users to sign up**. يظل تأكيد البريد العام مفعّلًا كإعداد احتياطي، مع Auto Confirm لكل حساب تنشئه إداريًا. إعداد config.toml يخص التشغيل المحلي؛ الموصل لا يستطيع تعديل خيار التسجيل المستضاف، وهذه خطوة مطلوبة من المالك.
6. ادخل الموقع باستخدام البريد وكلمة المرور. لا يحتاج هذا التدفق SMTP أو إعداد روابط رسائل.
7. التسجيل الذاتي واستعادة كلمة المرور بالبريد مخفيان في النسخة الحالية؛ إعادة التعيين تتم إداريًا. لم ننشئ حسابات أو كلمات مرور نيابة عنك.
8. اختبر الدخول بعد إنشاء الحسابين. لا تستخدم user_metadata لمنح الصلاحيات، ولا تحذف سجلات الشريك التاريخية عند إلغاء وصوله.

## Cloudflare

المخرجات `out/` ملفات فعلية جاهزة، وليست mockup. اختر Pages Direct Upload أو Git build. صفحات المسارات تتضمن `index.html` لكل مسار. أرفق `_headers` و`sw.js` وmanifest والأيقونات. لا تستخدم محوّل Next.js Workers لأن التطبيق لا يحتاج SSR. اختر النطاق المجاني `pages.dev`.

موقع مراجعة ChatGPT الخاص مرتبط بملفات المشروع نفسها. لا تمنح الشريك رابطًا خاصًا بمالك ChatGPT باعتباره رابط الدخول النهائي؛ انشر النسخة المستقلة أولًا.

## التحقق والنسخ الاحتياطية

- راجع Supabase Security Advisor بعد كل ترحيل. يجب ألا تظهر أخطاء RLS أو دوال عامة ذات صلاحيات غير مقصودة.
- نفّذ السيناريوهات في `TESTING.md` على مشروع اختبار مستقل، ثم احذف بيانات الاختبار فيه. لا تختبر ببيانات أعمال وهمية في مشروع Sheep الإنتاجي.
- جهّز نسخًا من PostgreSQL ومن صور Storage بصورة دورية؛ نسخة SQL وحدها لا تحتوي ملفات الصور.
- الحذف المنطقي لا يوفر مساحة الملفات تلقائيًا. أي تنظيف نهائي يجب أن يحافظ على النسخ المطلوبة للمراجعة.
